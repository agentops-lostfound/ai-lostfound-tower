# LF-5 → LF-6 후보 검색 연결 준비

2026-11-05 정연우. LF-6 후보 공개 규칙과 현재 구현을 연결하기 위한 로컬 API 계약이다. 기존 공통 특징·MCP 계약을 바꾸는 문서는 아니다. 실제 본인인증·필수 동의 API는 아직 연결하지 않았다.

## 요청과 공개 응답

`POST /chat/questions`는 질문과 선택적인 검색 조건을 받는다. 검색 조건은 품목·색상·분실 날짜·호선·역만 받으며 권한을 나타내지 않는다.

```json
{
  "question": "확인한 설명으로 찾아줘",
  "search_context": {
    "category": "지갑", "color": "검정", "lost_date": "2026-11-04",
    "lost_line": "2호선", "lost_station": "해운대역"
  }
}
```

후보 카드에는 `candidate_no`, `category`, `color`만 반환한다. 실제 접수 번호·접수 역·보관 상태·점수·사진 경로·비공개 특징은 반환하지 않는다. `search_filter`의 날짜·역은 사용자가 입력한 조건이며 DB에서 찾은 접수 장소가 아니다. 응답에는 예측할 수 없는 `search_result_id`가 따로 포함된다.

```json
{
  "status": "items_found",
  "candidates": [{"candidate_no": 1, "category": "지갑", "color": "검정"}],
  "search_result_id": "서버가_발급한_임시_참조값",
  "item_search_performed": true,
  "reservation_created": false
}
```

`id_verified`, `consent` 같은 클라이언트의 인증 완료 주장은 권한으로 사용하지 않는다. 검색 조건 안에 넣으면 거절한다. 실제 검색에는 서버 검증기가 확인한 Bearer 세션과 분실 날짜·호선·역이 필요하다.

## 인증 담당 서버와 연결할 지점

LF-6 서버가 기존 인증·필수 동의·만료·철회 상태를 확인하는 함수를 제공한다. 단순히 토큰이 있는지나 본문의 체크값을 검사하는 함수를 사용하지 않는다.

```python
agent = SearchAgent(
    database=PostgresItemSearch(os.environ["LF_CHAT_DATABASE_URL"]),
    authorize=verify_existing_find_session,
)
chatbot = Chatbot(guide, search=agent)
app = create_app(service, guide, chatbot)
```

`verify_existing_find_session(token)`은 해당 토큰이 유효한 본인인증·필수 동의 완료 세션일 때만 정확히 `True`를 반환해야 한다. 현재 `from_environment()`에는 검증기가 없으므로 실제 DB 설정만 켜도 조회가 열리지 않는다. 가상 인증 성공 버튼·공개 토큰 발급 API는 추가하지 않았다.

## 후보 선택을 내부 실제 물건에 연결

LF-6 서버 내부에서만 다음 메서드로 선택한 후보를 실제 번호에 연결한다.

```python
item_id = agent.resolve_candidate(search_result_id, candidate_no, verified_session_token)
```

- 현재 세션을 다시 검증하고, 결과가 생성된 토큰과 일치하는지 확인한다. 후보 번호만으로 물건을 선택할 수 없다.
- 참조값은 기본 10분 뒤 만료된다. 잘못된 번호·다른 토큰·인증 철회·만료는 다시 검색하도록 거절한다.
- 서버 메모리에는 원문 Bearer 토큰 대신 프로세스별 키로 만든 소유자 해시를 보유한다. 전체 256개, 같은 토큰 8개까지이며 오래된 자기 결과는 새 검색으로 교체될 수 있다.
- 공개 HTTP의 실제 번호 조회 API는 만들지 않았다. 메서드 반환값은 LF-6의 확인 질문·직원 판단 등 내부 절차에서만 사용해야 한다. 현재 보관 상태를 재확인하고 기존 승인·예약 관문을 적용해야 한다.
- 토큰이 교체되거나 서버가 재시작되면 다시 검색해야 한다. 현재 메모리 구현은 다중 서버용 세션 저장소가 아니다.

## 검색 동작과 미구현 범위

- 분실 날짜의 한국 시간 00:00 이후 접수를 조회한다. 같은 날짜에 접수된 것만으로 제한하지 않으므로 뒤늦게 접수된 물건도 포함할 수 있다. 미래 접수·인계 완료 물건은 제외한다.
- 품목·색상·날짜·호선 조건을 유지한 채 입력한 역을 먼저 조회한다. 그 결과가 비었을 때만 같은 호선으로 넓힌다. 같은 역에 일부 결과가 있으면 다른 역 후보로 세 개를 채우지 않는다.
- 호선만 주어진 가상 검색은 그 호선으로 제한한다. 실제 조회에서는 날짜·호선·역을 모두 요구한다. UI 확인 조건은 새 질문의 명시적 값으로 덮어쓸 수 있고, 새 품목을 말하면 이전 품목의 색·장소 조건을 물려받지 않는다.
- 고정 SQL·매개변수·읽기 전용 반복 읽기 거래·쿼리 시간 제한을 사용한다. 두 단계의 역 우선/호선 검색은 같은 DB 스냅샷을 사용한다.
- 현재 정렬은 접수 시각 최신순이며 LF-20 매칭 점수 상위 3개를 구현한 것은 아니다. 가린 사진·확인 질문·예약·키링 등 추가 특징 검색도 LF-6/LF-20 연결이 남아 있다.

## DB 구분

이 조회 연결부는 `center/schema.sql`의 `item`, `machine` 표를 대상으로 한다. 새 Docker 샘플의 `backend/init.sql`은 `items` 등 별도 표를 사용하는 다른 스캐폴드다. 같은 DB라고 가정해 접속하거나 자동 변환하지 않는다. 실제 팀 DB를 변경하거나 마이그레이션하는 작업은 이번 준비에 포함하지 않았다.
