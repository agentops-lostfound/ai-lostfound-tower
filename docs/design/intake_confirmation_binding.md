# LF-5 접수 확인과 사용자가 본 초안 연결 — 후속 구현 명세

2026-11-11 정연우. **확인 프로토콜을 로컬 구현하고 검증했다. 원격 게시·운영 적용은 별도다.**

## 11/12 추가 — 입력창에서도 현재 요약 확인

확인 버튼에는 증표가 붙었지만 입력창에 같은 `접수할게요`를 쓰면 증표가 없어 확인 단계가 반복됐다. 위젯은 현재 표시한 최신 `intake_confirm` 응답의 유효한 확인 값을 메모리에 보관하고, 명확한 확인 표현을 입력창에서 보낼 때만 함께 보낸다. `네, 이대로 접수해 주세요` 같은 자연스러운 표현도 처리한다.

- 서버는 여전히 증표 없는 문구만으로 저장하지 않는다. 원래 세션·업무·버전·만료·토큰 검사를 유지한다.
- 수정/부정/질문/권한 우회가 섞인 문장은 입력창이 확인 증표를 붙이지 않고, 서버도 명확한 동의로 해석하지 않는다.
- 이전 버튼은 자신이 표시한 요약의 증표를 유지한다. 최신 것으로 자동 교체하지 않는다. 재시도도 처음 보낸 값을 유지한다.
- 확인값은 다음 전송 시작·일반 안내 응답·완료·대화 지우기 때 해제하며 대화 저장소/이력에 넣지 않는다. 새로고침 후에는 요약을 다시 받아야 한다.
- 취소 확인 중 접수·등록·신고 표현으로 취소를 확정하지 않는다. 업무가 다른 동의를 섞지 않는다.
- 접수 여부/버튼 혼란 질문은 저장 없이 현재 초안을 보존하고 아직 접수 전임을 알려 준다. 요약은 줄을 나눠 표시한다.

공유 회귀 문항 `tests/confirmation_language_cases.json`은 명확한 동의18개·혼합/부정/질문16개다. Python과 위젯이 같은 문항을 검사한다. 아래 최초 문제 설명은 11/11 당시 이력이다.

## 확인된 문제

현재 서버는 자신의 confirm_version과 version을 비교하지만, 클라이언트 확인 요청에는 사용자가 본 초안 버전이 없다. 위젯은 질문 문구와 session_id를 보낸다. 따라서 초안3 요약을 본 뒤 초안4로 수정된 상황에서 늦게 도착한 ‘접수할게요’는 새 확인과 구별되지 않고 초안4를 저장할 수 있다.

가상 창구 감사에서 초안3→4 변경 후 같은 확인 문구로 저장1회를 확인했다. 이는 실제 운영 DB 침해 시험이 아니라 요청 구별이 불가능한 상태를 재현한 것이다. 중복 클릭·동시 요청의 한 번 저장 방어는 별도로 존재한다.

## 구현한 프로토콜

1. 서버가 확인 요약을 만들 때 해당 session·업무 종류·초안 버전에 묶인 무작위 확인 토큰을 발급한다. 모델에 토큰을 넘기지 않는다.
2. 화면이 표시한 요약의 draft_version과 confirmation_token을 확인 버튼에 보관한다. 버튼 클릭은 intake_action의 확인 요청으로 두 값을 함께 보낸다. 본인 확인 양식의 identity action과 구분한다.
3. 서버는 형식·세션·업무 종류·초안 버전·만료·토큰을 검사한 뒤에만 기존 접수/취소 창구를 부른다. 값 변경·취소·만료 시 토큰을 무효화한다.
4. 이전 토큰이나 다른 세션의 토큰은 저장하지 않고 새 요약을 보여 준다. 형식 오류와 유효기간/초안 불일치를 구분한다.
5. 단순 ‘네’ 또는 확인 문구만 온 요청은 저장하지 않고 확인 버튼을 다시 안내한다. 구형 호출 경로를 남겨 토큰 검사를 우회하지 않게 한다.
6. 같은 성공 토큰의 재전송은 기존 성공 결과를 반환한다. 동일 프로세스의 동시 요청은 기존 잠금으로 보호한다. 재시작 후 중복 방지는 별도의 영속 idempotency 저장소가 필요하다.
7. 원문 토큰은 trace·로그·모델 프롬프트에 남기지 않는다. 재시도·실패 기록에는 성공/거절 이유만 남긴다.

## 함께 바꿀 범위

- agents/chat_intake.py: action 모양, 요약 발급, 모든 저장 진입 검사, 무효화·재전송 처리.
- agents/chat_api.py: 확인 action 검증과 전달. 내부 함수만 고쳐 공개 HTTP 우회가 남지 않게 한다.
- web/chat-widget/widget.js: 요약별 확인 버튼, 요청 토큰, 재시도 시 동일 요청 유지, 대화 삭제/취소 시 무효화.
- evaluation/chat_eval.py 및 시험: 실제 화면처럼 직전 요약의 확인 값을 전달. 문구만 보내던 기존 대역을 마이그레이션하되 우회 경로는 남기지 않는다.

## 완료 판정

- 초안 변경 전 버튼·다른 세션·만료·토큰 누락·잘못된 토큰은 저장0회.
- 같은 토큰 동시 클릭·성공 응답 유실 후 재전송은 저장1회.
- 수정·취소·새 접수 후 이전 토큰 재사용은 저장0회.
- 분실·습득·찾기 요청 취소 세 경로와 공개 HTTP·위젯을 모두 확인.
- 창구가 저장한 뒤 응답 전에 실패하는 경우는 영속 중복 방지 계약 없이는 안전 재시도를 보장하지 않는다. 완료 여부 불명 상태를 별도로 안내한다.

실제 인증·동의 확인이나 영속 저장을 이 토큰이 대신하지 않는다. 세션 위조 방지·영속 복구는 후속 과제로 유지한다.

## 현재 HTTP·화면 약속

`/chat/questions`의 `status=intake_confirm` 응답은 최상위 `confirmation`을 함께 준다.
모양은 `{type: "confirm", draft_version: 정수, confirmation_token: 무작위 URL-safe 43글자}`다.
확인 버튼은 해당 값을 그대로 `intake_action`에 넣어 확인 문구와 함께 보낸다. 신분 확인 `identity` action은 그대로 유지한다.

잘못된 형식은 HTTP422. 누락·이전 초안·다른 세션 토큰은 저장하지 않고 현재 요약을 다시 준다.
만료되거나 더 이상 확인 단계가 아니면 실패 안내를 준다. 이들은 HTTP200 업무 응답이며 새 접수를 자동 시작하지 않는다.
성공한 동일 확인 재전송은 저장 없이 이전 성공 결과를 돌려준다. 토큰 없는 구형 확인 버튼은 저장하지 않는다.

토큰은 접수 엔진의 메모리에만 두며, Chatbot.ask가 trace를 마친 뒤 화면 응답에 붙인다.
들어온 토큰은 ContextVar에만 보관하고 그래프 상태에는 confirm 종류만 전달한다. HTTP 스트림의 최종 응답에도 같은 값을 준다.
실제 모델·trace에 토큰이 들어가지 않는지 그래프 입출력 검사로 확인한다. 위젯은 요약별 값을 복사해 버튼과 재시도 요청에 유지한다.

접수 실행이 성공했으나 창구 응답이 유실된 경우, 이번 변경은 그 요청의 즉시 재전송으로 다시 저장하지 못하게 할 뿐 성공 결과를 복구하지 못한다.
프로세스 재시작·새 대화에서의 재접수까지 한 번 저장을 보장하려면 영속 idempotency 계약이 필요하다.

후속 구현: [저장 완료 여부 불명](intake_uncertain_outcome.md). 응답 유실은 실패로 단정하지 않고 같은 대화의 재접수·재취소를 막는다. 완료 불명 기록은 일반 대화 TTL로 삭제하지 않으며, 자동 성공 조회·복구는 아직 없다.
