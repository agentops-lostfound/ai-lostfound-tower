# LF-5 접수 확인과 사용자가 본 초안 연결 — 후속 구현 명세

2026-11-11 정연우. **이 문서는 제안이며 아래 확인 프로토콜은 아직 구현하지 않았다.**

## 확인된 문제

현재 서버는 자신의 confirm_version과 version을 비교하지만, 클라이언트 확인 요청에는 사용자가 본 초안 버전이 없다. 위젯은 질문 문구와 session_id를 보낸다. 따라서 초안3 요약을 본 뒤 초안4로 수정된 상황에서 늦게 도착한 ‘접수할게요’는 새 확인과 구별되지 않고 초안4를 저장할 수 있다.

가상 창구 감사에서 초안3→4 변경 후 같은 확인 문구로 저장1회를 확인했다. 이는 실제 운영 DB 침해 시험이 아니라 요청 구별이 불가능한 상태를 재현한 것이다. 중복 클릭·동시 요청의 한 번 저장 방어는 별도로 존재한다.

## 권장 프로토콜

1. 서버가 확인 요약을 만들 때 해당 session·업무 종류·초안 버전에 묶인 무작위 확인 토큰을 발급한다. 모델에 토큰을 넘기지 않는다.
2. 화면이 표시한 요약의 draft_version과 confirmation_token을 확인 버튼에 보관한다. 버튼 클릭은 intake_action의 확인 요청으로 두 값을 함께 보낸다. 본인 확인 양식의 identity action과 구분한다.
3. 서버는 형식·세션·업무 종류·초안 버전·만료·토큰을 검사한 뒤에만 기존 접수/취소 창구를 부른다. 값 변경·취소·만료 시 토큰을 무효화한다.
4. 이전 토큰이나 다른 세션의 토큰은 저장하지 않고 새 요약을 보여 준다. 형식 오류와 유효기간/초안 불일치를 구분한다.
5. 단순 ‘네’ 또는 확인 문구만 온 요청은 저장하지 않고 확인 버튼을 다시 안내한다. 구형 호출 경로를 남겨 토큰 검사를 우회하지 않게 한다.
6. 같은 성공 토큰의 재전송은 기존 성공 결과를 반환한다. 동일 프로세스의 동시 요청은 기존 잠금으로 보호한다. 재시작 후 중복 방지는 별도의 영속 idempotency 저장소가 필요하다.
7. 원문 토큰은 trace·로그·모델 프롬프트에 남기지 않는다. 재시도·실패 기록에는 성공/거절 이유만 남긴다.

## 함께 바꿀 범위

- agents/chat_intake.py: action 모양, 요약 발급, 모든 저장 진입 검사, 무효화·재전송 처리.
- agents/chat_api.py: 확인 action 검증과 전달. 내부 함수만 고쳐 공개 HTTP 우회가 남지 않게 한다.
- web/chat-widget/widget.js: 요약별 확인 버튼, 요청 토큰, 재시도 시 동일 요청 유지, 대화 삭제/취소 시 무효화.
- evaluation/chat_eval.py 및 시험: 실제 화면처럼 직전 요약의 확인 값을 전달. 문구만 보내던 기존 대역을 마이그레이션하되 우회 경로는 남기지 않는다.

## 완료 판정

- 초안 변경 전 버튼·다른 세션·만료·토큰 누락·잘못된 토큰은 저장0회.
- 같은 토큰 동시 클릭·성공 응답 유실 후 재전송은 저장1회.
- 수정·취소·새 접수 후 이전 토큰 재사용은 저장0회.
- 분실·습득·찾기 요청 취소 세 경로와 공개 HTTP·위젯을 모두 확인.
- 창구가 저장한 뒤 응답 전에 실패하는 경우는 영속 중복 방지 계약 없이는 안전 재시도를 보장하지 않는다. 완료 여부 불명 상태를 별도로 안내한다.

실제 인증·동의 확인이나 영속 저장을 이 토큰이 대신하지 않는다. 세션 위조 방지·영속 복구는 후속 과제로 유지한다.
