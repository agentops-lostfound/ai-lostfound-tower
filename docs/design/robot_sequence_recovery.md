# SO-101 시퀀스 중단 후 복구·재개 계획

작성: 2026-11-11. **설계 단계이며 자동 재개는 아직 구현·활성화하지 않았다.**

## 현재 상황

후속 홈 복귀 구현은 `docs/handoff/2026-11-11-home-button-recovery.md`에 기록했다.
이 문서의 영속 체크포인트·자동 재개 프로토콜은 아직 계획이다.


- 관제탑 HTTP 응답 시간 초과 뒤 로봇 실행기의 5초 lease가 만료된 사례가 있다.
- 관제탑에는 `pose_5_open 이동 중`이 마지막으로 보였지만 로봇 실행기에는
  `pose_5_open 도착`과 `pose_5_target 시작`까지 있었다. 재개 기준은 실행기 기록이어야 한다.
- 현재 원격 실행기는 실패 시 작업을 취소하고 disarm한다. 재허용은 로컬 승인이다.
- 작업·진행 사건은 메모리에 있어 실행기 재시작 후 상세 복구 기준을 잃는다.
- 별도 통신 수정본은 응답 대기 5초, 독립 하트비트로 변경했으며 실행기의 lease 5초는 유지한다.
  관제탑 PC에 수정 파일 적용과 재시작이 필요하다.
- 이번 현장 복귀는 집게를 닫기 전 중단된 것을 확인하고
  `pose_5`로 집게 유지 후퇴 → `home` 순으로 수행했다. 다른 단계에 그대로 일반화하지 않는다.

## 목표와 범위

통신 지연은 같은 작업의 상태를 다시 받아 이어 보고,
실제 정지 뒤에는 현재 팔·물품·저장 경로를 검증한 복구 지점에서 이어 간다.
물품 기록이나 인계 완료를 추측으로 갱신하지 않는다.
사용자가 누른 정지는 자동 재개하지 않는다.

## 1. 먼저 통신 지연에 의한 불필요한 중단 줄이기

1. 준비된 응답 대기/독립 하트비트 수정본을 관제탑에 적용한다.
2. 상태 GET만 실패하고 하트비트가 정상인 경우, 제한된 시간 내에 같은 작업의 GET을 재조회한다.
3. 이때 작업 POST를 다시 보내지 않는다. 같은 `instance + job_id`의 상태를 받아야 한다.
4. 하트비트 유실·명시적 정지·통신 복구 시간 초과는 기존 정지 경로를 따른다.
5. 로봇에서 이미 완료된 작업이면 완료 기록을 다시 전달하고 동작을 반복하지 않는다.

자동 정지 유예를 길게 늘리는 방식으로 대체하지 않는다.

## 2. 실행기에 복구 체크포인트 저장

새 프로토콜/저널을 추가한다. 현재 메모리 사건 목록만으로 재개하지 않는다.

| 기록 | 내용 |
|---|---|
| 작업 식별 | case_id, item_id, slot_id, 원본 job_id, attempt/resume_id |
| 제어 소유 | instance/arm 세대, 승인 상태, 활성 작업, 정지 확인 여부 |
| 경로 버전 | 논리 시퀀스·실제 command_sequence·profile·보정 설정 해시 |
| 마지막 단계 | 마지막 도착 단계, 시작했으나 도착 미확인인 단계 |
| 팔 상태 | 촬영/수신 시각, 관절값, 집게 명령값, 관측값, 실제 HOLD 여부 |
| 물품 상태 | 미집기/파지 미확인/파지 확인/배출 미확인/배출 확인과 근거 |
| 정지 이유 | heartbeat_expired, operator_stop, motion_error, state_unknown |

도착 확인은 로봇 측에서 먼저 영속 저장하고 그다음 관제탑에 전송한다.
집게가 닫힌 것만으로 파지 확인으로 기록하지 않는다.
작업 종료·정지·재개 승인도 저널에 남기고 이력에서 비밀값과 사진은 제외한다.

## 3. 정지 이유에 따른 재개 정책

| 상황 | 처리 |
|---|---|
| 상태 조회 지연, 기존 작업 실행 중 | 같은 작업 조회를 복구해 계속 관찰 |
| 통신 lease 만료, 정지 확인됨 | 로컬 점검/재허용 뒤 복구 후보 생성 |
| 사용자 정지 버튼 | 계속 정지. 명시적 재개 요청 전까지 대기 |
| 충돌 의심·관절 오차·관측 끊김·정지 미확인 | 자동 재개 금지, 현장 확인 |
| 실행기 재시작·다른 제어자가 팔을 움직임 | 이전 작업 자동 재생 금지, 현재 상태 재확인 |

원격에서 arm 제한을 우회하거나 이전 세대의 요청을 재전송하지 않는다.
통신이 돌아왔다는 사실만으로 실제 정지가 해제되거나 재개 승인이 생기지 않는다.

## 4. 단계별 복구 경로

기존 티칭 파일에서 검증한 경로를 칸별로 명시한다. 관절값을 임의로 보간해 새 경로를 만들지 않는다.

| 중단 구간 | 복구 후보 |
|---|---|
| 집게 닫기 전 | 현재 자세가 허용 범위인지 확인 → 집게 유지로 해당 접근 자세 후퇴 → 필요 시 home → 같은 물품·칸을 재확인하고 집기 재시도 |
| close를 시작했으나 파지 상태 미확인 | HOLD 유지, 물품 파지 여부 확인 후 경로 선택 |
| 파지 확인 후 들어올리기·운반 중 | 기존 닫힘 명령을 유지하고 검증된 접근/운반 경유점으로 이동 → 배출 구간 재개 |
| 배출 open 전후 | 이미 내려놓았는지 확인. 물품이 없어진 칸에 다시 집기 명령을 보내지 않음 |
| 배출 확인 뒤 | 빈 팔의 복귀 경로만 수행하고 기존 반환 건에 결과 연결 |

팔의 집게 관측값만으로 물품 유무를 확정할 수 없다. 센서/영상 검증이 준비되지 않은 구간은
직원의 현장 확인을 받아야 한다. 집기·놓기처럼 물품 상태를 바꾸는 동작은 중복 실행하지 않는다.

## 5. 재개 전 확인과 실행

1. 이전 동작의 정지 확인, 새로 허용된 제어 세대, 단일 제어 소유권을 확인한다.
2. 최신 관절 관측과 HOLD, 동일 팔·경로/보정 버전, 해당 물품·칸의 DB 상태를 확인한다.
3. 도착 미확인 단계와 파지/배출 상태가 모호하면 재개하지 않는다.
4. 복구 계획에는 경유점, 집게 유지 여부, 재개 단계, 승인 유효기간을 넣는다.
5. 이전 체크포인트를 가리키는 일회성 resume_id로 실행한다. 같은 재개 요청의 재전송은
   기존 상태만 반환하고 새 동작을 만들지 않는다. 기존 취소된 job_id를 되살리지 않는다.
6. 복구 중 재실패하면 멈춘다. 통신 사유의 복구 시도도 작업당 1회부터 시작한다.

## 6. 구현 순서

1. 관제탑에 통신 안정화 수정 적용·지연 로그 수집.
2. 실행기에 정지 이유와 도착 체크포인트의 영속 저널 추가.
3. 칸별 `target → approach` 등 복구 경로와 관절 허용 범위를 현장 검증.
4. 로컬 복구/재개 API와 관제탑 재개 버튼 연결. 현재처럼 미구현 home 요청으로 다시
   disarm되는 흐름도 실제 검증된 복귀 절차로 교체.
5. 집기 전 구간부터 제한적으로 재개 도입. 파지·배출 상태 검증이 준비된 뒤 운반 중 재개 확장.

## 7. 검증 기준

- 상태 응답만 지연 / 하트비트 전체 손실 / 관제탑·실행기 재시작을 각각 재현.
- 모든 단계의 시작·도착 사이에 정지시켜 체크포인트와 실제 자세를 대조.
- 닫기·놓기 전후에는 실제 물품 상태를 확인하고 중복 집기/놓기·DB 중복 갱신이 없음을 확인.
- 중복 resume_id, 오래된 arm 세대, 바뀐 보정/시퀀스/물품 배정은 실행 전 거부.
- 사용자 정지 후 통신이 복구돼도 동작하지 않음.
- 복구 도중 정지 버튼과 통신 lease 만료가 계속 유효함.

처음 시연은 모의 HTTP/가상 모터에서 검증하고, 실물은 칸별로 집게 닫기 전 구간부터 검증한다.
