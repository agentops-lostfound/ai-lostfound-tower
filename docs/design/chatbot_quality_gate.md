# LF-5 대화 품질 검증 기준

화면의 증상 하나를 고친 결과만으로 배포 준비가 끝났다고 판단하지 않는다. 같은 사용자 여정을 수정 전후에 적용하고, 기존 기능·서버 상태·위젯 전송·실제 모델 응답을 나누어 확인한다.

## 고정 묶음

| 묶음 | 범위 | 판정 |
| --- | --- | --- |
| 기존 `chat_eval_500.json` | 안내·검색·이어 묻기·접수·직원 관제 | 기존 판정·기대 경로 유지 |
| 기존 창의/공격 500문항 | 개인정보·권한·안전·오접수·구어체 | 기존 판정 유지 |
| `conversation_quality_cases.py` | 253여정, 1,350턴. 8단계 개입·정정·업무 전환·명확/부정 동의·모호한 입력 | HTTP·초안·버전·다음 질문·업무 쓰기 횟수 |
| `conversation_quality_holdout.py` | 첫 후보 구현 후 작성한 추가 표현 40여정, 198턴 | 개발 묶음과 별도 성적. 첫 실패도 보존 |
| `conversation_quality_quiz.py` | 접수 후 소유 확인 질문 중 개입 12여정, 108턴 | 확인 질문 보존, 재접수 금지, 원래 질문 재개 |
| 공유 확인 문항 | 명확한 동의30개, 부정/혼합/질문22개 | Python·위젯 동일 문장 판정 |

253여정은 질문20개를 진행 단계8곳에 적용한 160개 여정을 포함한다. 같은 질문이어도 물건 종류·색·역·장소·요약·날짜·특징·본인 확인 단계에 따라 상태 오염이 달라 별도 여정으로 검사한다. 1,305개 문항/여정은 각기 다른 표현 1,305개라는 뜻이 아니다. 단위 시험의 여정 재실행이나 모델 재실행을 더해 고유 문항 수를 부풀리지 않는다.

추가 표현40개는 개발 묶음과 다른 표현이지만, 첫 검증에서 발견한 오류를 보완한 뒤 다시 실행했으므로 최종 성적은 미관측 시험 성적이 아니다. 모든 자유 표현의 정확도를 나타내지 않는다.

## 실행

운영 `.env`를 읽지 않고, 합성 데이터와 메모리 창구로 `/chat/questions`를 실제 호출한다. `conversation_quality.py`는 운영 연결 환경값을 제거한다. 실제 모델을 켜려면 로컬 Ollama의 Mi:dm을 사용하며 원격 서버·운영 데이터에 시험 접수를 만들지 않는다.

```powershell
python evaluation/conversation_quality.py --out outputs/journeys-01.json
python evaluation/conversation_quality.py --holdout --out outputs/holdout-01.json
python evaluation/conversation_quality.py --quiz --out outputs/quiz-01.json
python evaluation/conversation_quality.py --model midm-2.0-mini --only J001,J062,J169 --out outputs/midm-01.json
python -m unittest discover -s tests
node --test tests/test_chat_widget.cjs tests/test_chat_widget_window.cjs
```

실행기 `--source-root`로 고정된 이전 체크아웃을 지정할 수 있다. 평가 문항은 현재 평가기에서 가져오고 제품 코드만 이전 체크아웃에서 가져온다. 판정은 모델 출력으로 만들지 않는다. 준비 상태가 없으면 즉시 평가 준비 오류로 중단하고, 빈 상태 보존을 성공으로 세지 않는다.

결과에는 문항 의미 해시·평가기 해시·전체 agents 소스 해시·모델 호출 성공/오류·합성 여부를 남긴다. 실행 중 소스 변경은 종료 시 검사하며 성공 판정을 무효화한다. 기존 출력 파일은 덮어쓰지 않는다. `conversation-quality-stop.flag`가 생기면 다음 여정을 시작하지 않고 부분 기록을 보존한다. 과거 작업의 중단 표식은 지우지 않는다.

## 통과 조건과 한계

1. 기존 1,000문항과 새 305여정에서 실패가 없어야 한다. 기대 답이나 기존 채점기를 제품에 맞춰 낮추지 않는다.
2. 안내·감사·날씨·안전·개인정보 질문이 접수 값이나 확인 질문을 바꾸지 않아야 한다.
3. 명시적 정정은 해당 칸에 반영하고 확인 버전을 바꾼다. 같은 값을 다시 말했을 때는 유효한 확인을 무효라고 판정하지 않는다.
4. 다른 물건 이야기와 현재 업무 정정을 구별한다. 명시적으로 종류를 정정하면 물건 정보는 유지하되 역·날짜·본인 확인 등 이전 업무의 값을 복사하지 않는다. 접수 후 확인 질문 중에는 다른 신고로 바꾸지 않는다.
5. 소유 확인 질문 중 개입은 같은 질문으로 돌아가야 한다. 요약 승인 단계로 되돌리거나 같은 분실 접수를 다시 만들지 않는다.
6. 수정 전 버튼·증표 누락·부정/혼합 동의는 쓰기0회, 정상 접수·재전송은 의도한 쓰기1회여야 한다. 취소 확인과 등록 동의를 섞지 않는다.
7. 실제 위젯의 입력·Enter·과거 버튼·대화 삭제를 모바일/PC Chrome에서 확인한다. 합성 서버와 버퍼링된 NDJSON 전송 검증은 실제 운영 환경·스트림 도착 시점 검증과 구분한다.
8. Mi:dm을 실제 켠 별도 여정에서 호출 실적과 오류를 확인한다. 모델을 켠 여정의 모든 답변이 모델 생성 답변은 아니다. 보호 답변·접수는 코드가 처리한다.

자동 통과 뒤에도 실제 답변의 결론이 첫 문장에 있는지, 필수 사용자 행동을 빠뜨리지 않았는지 읽어 본다. 위치 결론과 수령 완료 행동을 별도로 검사한다. 구조 검사 기준을 강화할 때는 이전 실제 답변에도 동일하게 재적용하고 원본과 재판정 이력을 보존한다. 기존 전체 검사와 실제 모델 최종 검사는 소스를 고정한 뒤 수행하며, 중간 후보의 실패를 보완한 경우에만 다시 실행한다.

모델·프롬프트·운영 인증·DB·로봇 연결까지 통합 완료했다는 의미는 아니다. 정상 판정 후 같은 대규모 시험을 끝없이 반복하지 않는다. 새 변경·실패가 있을 때 해당 묶음을 재검증하고 최종 전체 검사를 수행한다.
