# LF-5 영속 작업 ID·조회 계약 시제품

2026-11-11 정연우. **제안 계약과 독립 대역 검증**이며 운영 연결 완료가 아니다.

## 확인한 팀 상태

인계 기준 로컬 HEAD는 `67c1cbb`, 브랜치는 `LF-5-jeongyeonwoo-integration-validation`이며 시작 시 변경은 없었다.
GitHub 읽기 비교에서 기준 main `43d973b` 이후 12개 커밋을 확인했다. 최신 main의
`SimDirector.found(text)`, `lost(text, opts)`, `answer(pending_id, text)`,
`cancel_claim(claim_id, id_no_masked, by_staff)`에는 공통 작업 ID·결과 조회 인자가 여전히 없다.
조회한 파일 blob은 `sim_director.py=4a58758aee072ad827d22f2f106f24113d52a66b`,
`chat_intake.py=57aac3f37e1afdecef06899d404140cf73114425`다.

팀 변경에는 초량·중앙 역 전환, 로고 별칭, 키오스크/관리 화면 보완 등이 있다.
이번 변경은 새 독립 모듈·시험·문서만 추가한다. 팀 main의 12개 커밋을 로컬에 통합하지 않았으며,
이 시제품 검증 결과를 최신 main 통합 검증으로 해석하지 않는다.

## 두 저장소의 책임

| 구성 | 보장하는 범위 |
|---|---|
| `OperationJournal` | 저장 전 작업 ID 영속화, 같은 수락 초안의 동일 ID, 요청 내용 결합, 실행권 원자적 획득, 불명 기록 보존 |
| `OperationDesk` | 작업 ID별 업무 효과와 영수증을 **같은 업무 DB 트랜잭션**에 저장, ID 재전송 중복 제거, 권한 있는 정확한 결과 조회 |
| `tests/intake_operation_fixture.py` | 위 창구 계약을 검증하는 별도 SQLite 대역. 팀 DB/SimDirector/로봇을 호출하지 않음 |

챗봇 장부만 추가해서 기존 창구를 호출하면, 업무 저장과 장부 확정 사이의 장애를 제거할 수 없다.
따라서 기존 창구를 자동으로 감싸지 않는다. 업무 효과와 영수증의 원자성을 창구 담당자와 먼저 합의해야 한다.
로봇·비동기 후속 작업까지 한 번 실행하려면 창구의 영속 outbox와 소비자별 중복 제거 계약도 필요하다.
대역의 `business_effects` 한 행은 업무 DB 변경만 나타내며 실물 동작 보장이 아니다.

## 서버 내부 호출 약속

1. 실제 인증 어댑터가 `Owner(subject, auth_session)`를 만든다. 화면의 `session_id`, 가린 이름·신분 값은 인증 근거가 아니다.
2. 기존 초안 확인 검사를 통과한 뒤 `prepare(owner, confirmation_id, kind, payload)`를 호출한다.
   `confirmation_id`는 서버가 발급하고 재전송·재시작에도 복원하는 **수락 초안의 고유 ID**다.
   숫자 `draft_version` 하나나 새 요청마다 만드는 난수로 대체하지 않는다.
3. 장부의 `prepared` 저장이 끝난 후에만 `dispatch`한다. 장부를 열거나 저장하지 못하면 업무 창구를 호출하지 않는다.
4. 첫 실행권을 얻은 작업자만 `desk.execute(operation, payload)`를 호출한다.
   나머지 작업자와 불명 작업의 재전송은 읽기 전용 `recover`/`lookup`으로 간다.
5. 조회 영수증의 `operation_id`, `owner_scope`, `kind`, `request_hash`가 전부 같을 때만 복구한다.
   없음·오류·다른 요청·잘못된 결과 번호이면 `uncertain`을 유지한다. 검색 후보로 성공을 추정하지 않는다.

`kind`는 `found/lost/answer/cancel_claim`이다. 확인 질문 답변은 최초 lost 작업과 별개 ID를 받되,
실제 연결 시에는 본인 소유 pending 작업과의 부모 관계·답변 순서를 창구가 확인해야 한다.
`Operation`은 서버 내부 자료형이며 전체를 웹·모델·trace로 내보내는 계약이 아니다.
현재는 HTTP 경로, 위젯 버튼, 기본 생성자 연결, 환경변수를 추가하지 않는다.

| 상태 | 의미 | 자동 재저장 |
|---|---|---|
| prepared | 저장 전 발급된 작업. 아직 창구 실행권을 얻지 않음 | 최초 dispatch만 가능 |
| running | 실행권 획득/창구가 실행 중임을 확인 | 금지, 조회만 |
| completed | 정확한 창구 영수증으로 이 명령의 결과 확인 | 금지, 결과 재사용 |
| rejected | 정확한 창구 영수증으로 업무 거절 확인 | 금지, 결과 재사용 |
| uncertain | 전달 여부/처리 결과를 확인할 증거 부족 | 금지, 조회만 |

`completed`는 명령 완료다. lost의 `pending_id`는 질문 대기, `wait_id`는 분실 신고 대기이며
반환·본인 인증·로봇 인계 완료를 뜻하지 않는다. 현재 시제품은 결과 ID만 보관한다.
실제 화면 복구에 필요한 질문·단계·안전한 표시 정보의 버전 계약은 후속 합의가 필요하다.
이미 확정된 결과는 늦은 조회 실패로 불명 상태로 되돌리지 않는다. 시간 만료로 불명 기록을 삭제하지 않는다.

## 권한·개인정보·보관

장부는 원문 초안, 가린 신분 정보, 실제 사용자/인증 세션 ID, 확인 토큰, 오류 원문을 저장하지 않는다.
소유자·초안 ID·요청 내용은 도메인을 분리한 HMAC-SHA256으로 결합한다.
결과는 허용한 `item_id/claim_id/wait_id/pending_id`만 받는다. 빈 값·공백·bool·120자 초과 ID는 거절한다.
장부와 창구 모두 다른 소유자 조회를 없는 작업과 같은 오류로 처리한다.

HMAC 키는 32바이트 이상으로 명시 주입하며, 기존 키·DB 파일·서버 인증 세션을 재시작 후에도 유지해야 한다.
기본 키·`.env` 로딩은 없다. 키를 바꾸거나 인증 세션을 새로 만들면 같은 작업에 대한 접근 연속성이 없다.
키 교체·인증 갱신·기기 변경 시 소유권 이전은 인증 담당자와 별도로 정해야 하며 클라이언트가 지정할 수 없다.
파일 접근 권한·암호화·백업·보관 기한·운영자 감사/대조/해제 절차는 운영 계약으로 남겨 둔다.
HMAC만으로 장부의 결과 ID까지 익명화되는 것은 아니므로 장부 파일도 보호 대상이다.

이 Python 자료형은 인증 구현이 아니다. 신뢰된 서버 어댑터 밖에서 호출하도록 노출하면 안 된다.
창구는 인증된 서비스 호출만 받고, 요청 해시와 실제 payload 결합을 검증하는 계약이 필요하다.
시험 대역은 같은 프로세스의 신뢰된 호출자를 전제로 하며 네트워크 인증을 구현하지 않는다.
새 확인 ID로 유사 내용을 보내는 의미상 중복은 자동 차단하지 않는다. 실제 연동 전에는 영속 미확정 작업을
복원하여 새 대화/다른 화면의 접수도 막는 정책이 필요하다.

## 검증 후 다음 연결 순서

- 창구 담당자: 실제 업무 DB에 영수증과 업무 변경을 원자적으로 남기는 방법, 저장 거절/미발견의 의미, outbox 합의.
- 인증 담당자: 서버 주체·세션, 권한 확인, 갱신/다른 화면 연결, 수락 초안 ID 영속 복원 합의.
- 챗봇: 위 계약을 만족하는 창구와 장부를 명시 주입하고 기존 확인 검증 뒤 연결. 기존 불명 보호는 그대로 유지.
- 화면: 최소 결과 표시 계약을 통해 조회/복구. 웹 임의 해제·재저장 버튼은 만들지 않음.
- 운영: 실제 기록 대조와 감사 가능한 복구/거절 절차·보관 정책 합의 후 통합 시험.

팀 스키마·인증 계약은 수정하지 않았다. 운영에서 응답 유실 자동 복구/재시작 중복 방지가 구현됐다고 설명하면 안 된다.
