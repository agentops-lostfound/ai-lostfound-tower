# LF-5 저장 완료 여부 불명 상태

2026-11-11 정연우. 로컬 구현, 운영 반영은 별도.

## 상태와 실행 정책

접수(found/lost), 확인 질문 답변(answer), 찾기 요청 취소(cancel_claim)를 실행한 뒤 응답 유실·잘못된 응답·예상하지 못한 오류가 나면 저장했을 수 있다. 이를 실패로 확정하지 않고 `status=intake_uncertain`, `intake.stage=uncertain`, `retry_allowed=false`로 안내한다.

서비스의 명시적 업무 거절 타입(RequestError·NotFound·Conflict)은 기존 실패 응답으로 유지한다. 문자열 클래스 이름만 같은 오류는 업무 거절로 신뢰하지 않는다.

불명 상태에서는 같은 세션의 확인 재전송·새 접수 시작·취소 문구가 모두 기존 불명 결과를 반환한다. 저장 도구를 다시 부르지 않는다. 감독도 새 작업을 추가하지 않고 안내로 끝낸다. 위젯은 완료·실패 대신 결과 확인 필요로 표시하며 재시도 버튼을 만들지 않는다.

## 보관 범위

불명 상태는 현재 프로세스의 해당 세션에 보관하고, 일반 대화 TTL로 자동 삭제하지 않는다. 만료 직후 재접수되는 문제를 막기 위해서다. 원래 초안·신분 정보·확인 토큰은 버리고 업무 종류와 안전한 안내만 보관한다.

이는 영속 저장소가 아니다. 프로세스 재시작·새 세션·다른 화면까지의 중복 방지를 보장하지 않는다. 사용자에게 다른 화면에서도 같은 요청을 다시 보내지 말고 처리 여부를 확인하도록 안내한다. 장기 운영에는 확인·해제 절차와 보관 정책, 영속 작업 기록이 필요하다.

## 조회·복구의 현재 한계

현재 창구에는 요청 식별자 기반의 공통 작업 결과 조회 계약이 없다. 응답을 못 받았다면 접수 번호조차 모를 수 있으므로, 비슷한 물건을 조회해 성공으로 추측하지 않는다. 자동 성공 판정·자동 재저장·불명 상태 해제 기능은 추가하지 않았다.

다음 구현에는 저장 전에 발급한 서버 작업 ID, 창구의 영속 idempotency, 본인 확인을 통과한 읽기 전용 작업 상태 조회, 완료·거절·실행 중·불명 응답이 필요하다. 조회 결과와 원래 요청을 대조한 뒤에만 성공 복구나 재확인을 허용해야 한다.

신규 안내는 실패를 숨기거나 저장 성공을 보장하는 기능이 아니다. 완료를 모르기 때문에 재실행을 멈추는 보호다.
