# 관제탑 메인 AI — 매칭이 애매할 때 에이전트들이 함께 근거를 모으는 구조 (11/8 변재원)

한줄 설명: 반환 흐름이 "어느 물건을 꺼낼지 애매하다"에서 멈추면, 바로 직원을 부르지 않고 관제탑 메인 AI가 매칭·보관 칸·비전 에이전트에게 일을 시켜 근거를 더 모은 뒤 결론을 낸다.

## 1. 왜 만들었나

README 의 처음 구상은 "메인 AI 와 하위 에이전트로 이뤄진 AI 관제탑이 전체 과정을 관리"였다. 그런데 11/7 까지의 관제탑은 정해진 6단계(웹 관문 → 방문 관문 → 탑뷰·매칭 → 사전 접근 → 집기 → 전달)를 순서대로 실행하는 규칙 흐름(`agents/supervisor.py`)이었고, AI 는 "보류"만 할 수 있는 검토(`agents/llm_reviewer.py`)뿐이었다. 에이전트끼리 주고받는 장면은 챗봇 쪽에만 있었다.

그래서 반환 흐름에서 사람이 가장 자주 불려 오는 지점인 **매칭이 애매할 때**를 골라, 메인 AI 가 하위 에이전트를 지휘하는 구조를 붙였다. 규칙 흐름은 그대로 두고 그 위에 얹었기 때문에 메인 AI 를 끄면(`TOWER_BRAIN=0`) 예전과 완전히 같다.

## 2. 구조

```
반환 흐름 3단계 locate: 탑뷰 촬영 → 매칭
        |  매칭 '애매(uncertain)' 또는 '닮은 물건 있음'
        v
  +------------------------------- 관제탑 메인 AI (LangGraph, agents/tower_brain.py) ----+
  |                                                                                       |
  |   main_ai (Mi:dm: 아직 안 부른 에이전트 중 다음 것을 고름, 이유 한 문장)               |
  |      |  ^          |  ^           |  ^                                                |
  |      v  |          v  |           v  |                                                |
  |  matching_agent  storage_agent  vision_agent                                          |
  |  왜 애매한지     보관 칸 기록   탑뷰를 다시 찍고                                      |
  |  후보·점수·차이  위치 안 후보   다시 매칭(한 번)                                      |
  |                                                                                       |
  |   conclude (코드가 결론): 다시 매칭이 '확실' + 닮은 물건 없음 → 반환 계속              |
  |                           그 밖 → 직원 확인 + 메인 AI 추천                             |
  +---------------------------------------------------------------------------------------+
        |
        v
  반환 계속(사전 접근 → 집기 → 전달)  또는  직원 확인 알림(추천 포함)
```

| 에이전트 | 하는 일 | 쓰는 것 |
|---|---|---|
| 메인 AI (`main_ai`) | 지금까지 모인 근거를 보고 다음에 부를 에이전트를 고른다. 근거가 충분하면 `finish` | Mi:dm 2.0 Mini (JSON 형식 강제). 모델이 없거나 이상한 답이면 정해진 순서(매칭 → 보관 칸 → 비전) |
| 매칭 에이전트 | 찾는 물건 특징, 후보 3개, 1위 점수, 2위와의 차이, 닮은 물건 여부를 정리 | 매칭 부품 결과(`match_item`) |
| 보관 칸 에이전트 | 이 물건이 기록된 보관 칸과, 그 칸 구역 안에 있는 후보를 찾음 | 보관함 정답지(`agents/storage.py`)의 칸 기록 + 구역 작업대 좌표(`bounds_mm`) |
| 비전 에이전트 | 탑뷰를 한 번 더 찍고 다시 매칭. 확실해지면 닮은 물건 검사까지 다시 함 | 탑뷰 부품(`vision_topview`) + 매칭 부품 |

## 3. 안전 원칙 — 메인 AI 가 할 수 없는 것

- **로봇을 움직이라고 결정할 수 없다.** 반환을 계속하는 조건은 처음과 같다: 매칭 부품이 '확실(matched)'을 내고, 닮은 물건 검사(`lookalike`)를 통과해야 한다. 이 확인은 메인 AI 결과를 받은 뒤 `supervisor.locate` 가 코드로 한 번 더 한다
- 메인 AI 가 하는 일은 "어느 에이전트를 부를지"와 "직원에게 줄 추천" 두 가지뿐
- 메인 AI 에서 오류가 나면 직원 확인(`메인 AI 오류(…)`)
- 대화가 무한히 돌지 않게 최대 4번, 비전 재촬영은 1번

추천 문장은 근거가 같은 쪽을 가리킬 때만 후보 번호를 말한다.
- 매칭 1위와 보관 칸 위치가 같은 후보 → "추천: 후보 2번 — 매칭 1위이고 보관 칸 기록 위치와도 맞음(직원 확인 후 진행)"
- 보관 칸 위치만 하나를 가리킴 → "추천: 후보 2번 — 보관 칸 기록 위치와 맞음(매칭 1위는 1번, 직원 확인 필요)"
- 그 밖 → "추천 없음 — 근거가 한쪽을 가리키지 않음, 직원이 안쪽 특징 확인"

## 4. 어디서 보이나

| 곳 | 보이는 것 |
|---|---|
| `/live` 화면 오른쪽 "🤖 관제탑 메인 AI · 에이전트 대화" | 메인 AI(보라)와 에이전트(초록)가 주고받는 말풍선. 처음 대화가 생기면 나타남 |
| 디스코드 관제 채널(progress) | `[사례번호] 🤖 메인 AI` / `🤖 매칭 에이전트` … 같은 내용 |
| Langfuse (us.cloud.langfuse.com) | trace 이름 `tower-main-ai`, 세션 = 사례 번호. 나무: `tower-brain-graph` → `main_ai`(안에 `main-ai-llm` 모델 호출) · `matching_agent` · `storage_agent` · `vision_agent` · `conclude` |

## 5. 켜는 법과 가상 시연

1. `.env` 에 `TOWER_BRAIN=1` (모델은 `TOWER_BRAIN_MODEL`, 비우면 챗봇과 같은 `LF_CHAT_RAG_MODEL` = `midm-2.0-mini`)
2. 관제탑을 다시 켠다(`TOWER_SIM=1` 가상 시연)
3. 분실 신고 메시지 끝에 `#흐린촬영` 을 붙인다. 예: `블루 모형폰 잃어버렸어요 #흐린촬영`
   - 첫 탑뷰에서 색·글자를 못 읽은 것처럼 만든다 → 화이트·블루 모형폰이 구별되지 않아 매칭 애매
   - 메인 AI → 매칭 에이전트("후보 1번·2번 모형폰, 차이 0") → 보관 칸 에이전트("기록 칸 R1-2 안 후보: 2번") → 비전 에이전트("다시 찍어 보니 확실: 2번") → 결론: 반환 계속 → 인계 완료
   - `TOWER_BRAIN=0` 이면 같은 메시지가 "매칭 불확실 — 자동 반환 안 함"(직원 확인)으로 끝난다 — 두 결과를 나란히 보여 주면 메인 AI 의 역할이 잘 드러난다
4. 실제 보관함에서 보관 칸 에이전트가 위치로 후보를 가리려면 `/storage` 화면에서 구역마다 작업대 좌표(`bounds_mm`)를 넣어야 한다. 넣지 않으면 "좌표가 없어 위치로는 가릴 수 없어요"라고 말한다(가상 시연은 가상 작업대 칸 위치를 씀)
