# 새 대화 모델 프로젝트 연동·충돌 검증·최적화

2026-11-06 · 정연우 · 로컬 작업, GitHub/Jira 미게시

## 적용 결과

Qwen3 4B Instruct-2507 Q4_K_M을 사용하는 `model_rag` 경로를 관제탑 챗봇 API, 분실물 설명 입력 화면, 독립 위젯에서 같은 정책으로 생성하도록 통일했다. 사용자·도우미 대화 문맥은 모델에 전달하되, 후보 조회·권한·회수 상태·승인 문서는 서버가 관리한다. 모델에는 SQL 실행이나 본인인증·예약·반환·로봇 실행 권한을 부여하지 않았다.

현재 실행 주소는 입력 화면 `http://127.0.0.1:8111/input`, 위젯 `http://127.0.0.1:8112/chat-widget/demo`다. 두 서버의 상태 응답에서도 모델과 엔진을 확인했다.

## 보완한 부분

| 항목 | 수정 및 검증 |
|---|---|
| 진입점별 설정 중복 | `agents/chat_factory.py`에서 모델·엔진 선택을 공통 처리. 위젯의 불필요한 이전 챗봇 생성과 가상 DB 중복 초기화 제거 |
| 설정 실수 | `model`/`legacy` 외 오타는 오류로 알림. 모델 우선순위와 기본값을 세 진입점에서 동일하게 검사 |
| 로컬 모델 응답 형식 | 생성·검토 응답의 객체·본문·완료 여부·크기 검사 공통화. 검토 응답도 1,000자 제한. 잘못된 응답은 이미 조회한 후보와 출처를 유지 |
| 동시 요청 | 모델 사용 중 두 번째 요청을 대기열에 무한 적재하지 않고 서버 근거 답변 반환. 검색 후보는 정상 조회되는지 검사 |
| 가상 데이터 오인 | 실제 조회 시 서버가 가상 DB 고지와 후보 미확정 안내를 보장. 이미 포함된 정형 문구는 중복 표시하지 않음 |
| 색상 제한 설명 | 실제 HTTP 대화에서 단일 연보라색을 복수 색상으로 잘못 설명한 답변 발견. 서버의 `unsupported` 판단과 충돌하면 모델 답변을 채택하지 않고 정확한 서버 안내 반환 |
| 입력 화면 안내 | 실제 답변 중 설명 정리 버튼만으로 검색 조건이 사용되거나 입력만으로 조회가 진행된다는 문장 발견. 화면 순서를 생성·검토 지시에 명시하고, 식별된 잘못된 실행 안내는 승인된 사용 설명 문서로 대체 |
| 상태 확인 | 입력 API의 `/health`에도 `chat_engine`, `chat_model` 추가. 설정 표시는 추론 성공 보장과 구분 |

## 프로젝트 기능 연동 검증

기존 회수 연동 시나리오를 이전 엔진과 새 `ModelChatbot` 엔진 양쪽에서 실행했다. 임시 SQLite에만 검색/회수용 연결 뷰를 만들고 가상 데이터로 다음을 확인했다. 실제 실행 중인 시연 DB나 팀 DB에 연결 뷰를 추가하지 않았다.

1. 설명 입력·확인으로 품목·색상·날짜·호선·역 검색 조건 생성.
2. 후보 조회와 수령 절차 안내를 함께 요청.
3. 회수 등록 후 운송 중인 물건이 검색 후보에서 제외됨.
4. 모델 장애 중에도 이미 조회한 결과와 회수 상태를 보존.
5. 일부 도착 기록 후 미도착 알림 유지.
6. 도착 완료 후 보관 상태의 물건이 다시 후보에 표시됨.
7. 중복 회수/도착 요청의 중복 기록 방지, 최종 회수 이벤트·알림·통계 정합성 확인.
8. 모델 요청과 공개 응답에 내부 물건 번호·인증 토큰이 전달되지 않는지 검사.

## 검증 결과와 해석

- 최종 통합 폴더: Python **869개 실행, 14개 제외, 실패 0**.
- 최종 LF-5 폴더: Python **865개 실행, 13개 제외, 실패 0**.
- 화면 JavaScript **41개 통과**, 입력 채팅 JS 문법 검사 및 `git diff --check` 통과.
- 보완 중 선정 모델로 22턴 실제 대화: 자동 상태·조건·출처·모델 채택 검사 22/22, 중앙값 2.82초, 최대 7.36초. 이는 해당 단계의 유한 시나리오 결과다. 본문 수동 검토에서는 화면 순서 문제를 발견했으므로 **22/22를 자연어 답변 전체의 정확도로 해석하지 않는다**.
- 이후 실행 서버 양쪽에서 각 7턴, 총 14턴 실제 HTTP 확인. 단일 미지원 색조를 복수 색상으로 설명한 답변을 확인하고 서버 근거 답변으로 대체하는 회귀 검사를 추가했다. 수정 후 해당 색조가 올바른 미지원 안내로 대체됨을 실제 서버에서 확인했다.
- 마지막 화면 안내 보완 후 양쪽 서버에서 각 2턴, 총 4턴 추가 실제 HTTP 확인: 글 입력 안내와 휴대폰 가상 후보 조회 정상. 모델이 작성한 답변이 채택되며 가상 DB·미확정 표시가 유지됐다.
- 응답 시간은 현재 PC의 로컬 관측값이며 성능 향상 보장이나 동시 사용자 부하 시험 결과가 아니다. 동일 질문 전체를 캐시하지 않으므로 회수 상태가 바뀐 뒤 오래된 후보를 재사용하지 않는다.

전체 검사 로그는 작업 공간 루트 `support_tests_project_model_integration.log`, `support_tests_lf5_project_model_integration.log`에 있다. 실제 대화 원문은 로컬 `.cache/project-model-integration-validation.json`, `.cache/project-model-final-http-validation.json`, `.cache/project-model-final-smoke-validation.json`에 보관했다. 가상 질문만 사용했다.

## 실행 및 연동 설정

```text
LF_CHAT_ENGINE=model
LF_CHAT_MODEL=qwen3:4b-instruct-2507-q4_K_M
```

환경값 이름과 용도를 `.env.example`에 추가했다. 실제 비밀 설정 파일은 읽거나 수정하지 않았다. 모델은 미리 설치되어 있어야 하며 시작 때 자동 다운로드하지 않는다. 모델 우선순위는 `LF_CHAT_MODEL` → 기존 `LF_CHAT_RAG_MODEL` → 선정 기본 모델이다. 엔진 미지정 시 기존 방식은 유지하므로 팀원이 새 모드를 실행할 때 위 설정을 명시해야 한다.

사진 분석 모델은 별도다. 이번 변경은 사진 모델이나 회수/검색 공유 계약을 바꾸지 않는다. 세 진입점의 가상 DB 선택 정책도 기존대로 유지한다. 실제 DB 설정이 있으면 모델 오류가 나더라도 가상 DB로 바꿔 조회하지 않는다.

## 남은 한계

- 실제 PostgreSQL·팀 본인인증/동의 세션·실제 로봇을 연결한 시험은 수행하지 않았다. 환경 의존 시험 제외 건수를 통과 건수로 세지 않았다.
- 모델 자체 검토만으로 모든 모순을 잡지 못한다. 이번에 발견한 구체적 오류는 서버 검증과 문서 대체로 보완했으나 모든 표현에 대한 정확성을 보장하지 않는다. 미세한 어색한 표현·오타 가능성도 남는다.
- 복수 색상·미지원 색조·키링/재질 같은 상세 특징 검색은 새로 지원하지 않는다. 모델이 검색 기능을 임의로 확장하지 않도록 서버 제한을 유지한다.
- 모델 대기 제한은 챗봇 인스턴스 내부 기준이다. 별도 프로세스인 사진 추론·다른 시연 서버와 동시에 GPU를 쓰는 상황의 GPU 전체 자원 중재는 별도 과제다.

## 변경 범위

`agents/`의 팩터리·API·모델 어댑터, `tools/`의 시연 진입점, `.env.example`, 관련 테스트와 위젯 안내 문서를 수정했다. 담당 경계를 넘는 API·도구 수정 이유는 세 화면의 동일 모델 설정과 호환성을 보장하기 위해서다. `agents/contracts.py`, `docs/contracts/mcp_tools.md`는 수정하지 않았다. main 병합·원격 게시·Jira 갱신은 수행하지 않았다.
