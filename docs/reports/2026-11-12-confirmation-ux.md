# LF-5 입력 확인 반복 및 접수 답변 개선

2026-11-12 · 정연우 · 기준 main `90d32b1` · 브랜치 `LF-5-jeongyeonwoo-confirmation-ux`

## 문제와 변경

사용자가 올린 화면처럼 요약을 보고 입력창에 `접수할게요`라고 쓰면 확인 안내만 반복될 수 있었다. 확인 버튼은 현재 초안의 확인 증표를 보내지만 입력창 전송은 보내지 않아 서버가 저장을 거절했다. 문장 인식과 화면 요청 연결을 함께 고쳤다.

- 입력창 전송과 Enter는 명확한 동의일 때만 현재 화면 요약의 확인값을 함께 보낸다. `네, 이대로 접수해 주세요!`, `신고 부탁드려요` 같은 표현을 처리한다.
- 수정·부정·질문·인증 우회가 섞인 문장은 동의로 처리하지 않는다. 서버의 세션·초안 버전·토큰·만료 검사는 유지한다.
- 과거 버튼은 과거 요약의 확인값을 유지한다. 최신 값으로 바꿔 주지 않는다. 재시도도 처음 보낸 요청을 유지한다.
- `접수된거야?`, `왜 자꾸 확인하래`에는 접수 전임과 다음 행동을 답하며 작성한 내용을 보존한다. 확인 요약을 줄바꿈해 구분한다.
- 이미 완료한 뒤 같은 말을 보내면 앞선 완료 메시지로 안내한다. 중복 저장하지 않는다.
- 취소 확인 중 접수·신고·등록 문구로 취소를 확정하지 않는다. 취소 단계의 안내도 실제 [네]/[아니요] 버튼과 일치시켰다.
- 확인값은 메모리에만 보관하고 다음 전송·일반 응답·완료·대화 삭제 때 비운다. 이력/로컬 저장소에 넣지 않는다.

Mi:dm 모델·프롬프트·검색 지식·인증 공급자는 변경하지 않았다. 이번 결과는 접수 확인 흐름과 관련 표현의 개선이며 모든 자유 문장의 이해도가 해결됐다는 의미가 아니다.

## 검증

- 공유 문항: 명확한 동의 18개, 혼합/부정/질문 16개. Python과 위젯이 같은 JSON을 검사한다.
- 신규 Python 6개 시험 메서드: 증표 없는 요청 거절, 유효 확인 한 번 저장, 재전송, 수정 전 증표 거절, 혼란 질문의 초안 보존, 실제 합성 HTTP 처리, 취소 업무 구분.
- Node 위젯/창 시험 36개 통과. 일반 입력·Enter 연결, 확인값 해제, 재시도, 이전 버튼·최신 입력 구분을 검사한다.
- 전체 `python -m unittest discover -s tests`: **1,888개, 실패 0, 제외 35**. 실제 DB 연결이 필요한 시험은 이번 작업에서 활성화하지 않았다.
- 실제 Chrome과 로컬 합성 서버에서 구형 위젯의 입력 반복, 개선 위젯의 Enter 접수, 재전송의 중복 방지, 수정 전 버튼 거절, 수정 후 자연어 확인을 검증했다. 성공한 두 접수 흐름은 각각 업무 쓰기 한 번이었다.

브라우저 전후 비교는 동일한 수정 백엔드에서 기준 커밋의 구형 위젯과 개선 위젯을 비교해 전송 원인을 분리했다. Mi:dm 답변 전후 평가가 아니다. Playwright가 실제 서버의 NDJSON 응답을 받아 그대로 버퍼링해 전달했으므로 스트리밍 도착 시점 검증과 구분한다. 브라우저 확인 후 추가한 취소 단계 안내/구분은 최종 Python·Node 시험으로 검사했다.

전체 시험 중 기존 `test_run_tower`의 backlog=1 연결이 Windows에서 남아 두 번째 포트 확인이 시간 초과되고 시험 안에서 실제 Uvicorn을 시작하는 정지를 발견했다. 해당 시험이 만든 프로세스만 종료한 뒤 최초 probe 연결을 accept/close하도록 시험을 수정했다. 운영 `tools/run_tower.py`는 변경하지 않았다. 중단된 `full01.log`를 성공 기록으로 세지 않으며 최종 결과는 `full04.log`다.

로컬 실행 증거: 작업 루트 `outputs/confirmation-ux-20261112`의 `browser-result.json`, `before.png`, `after.png`, `full04.log`. 합성 데이터만 사용했다. 대규모 500문항/실제 모델 반복 평가는 다시 실행하지 않았다.
