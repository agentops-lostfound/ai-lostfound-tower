## 추가 보강과 방어 확인

- SQLite 생성 시 `executescript`의 암묵적 커밋을 제거하여 스키마 준비·초기 데이터·시연 버전을 하나의 쓰기 거래에서 처리.
- SQLite 저장소 오류는 SQL·파일 경로·예외 원문을 반환하지 않는 일반 503으로 안내.
- 서로 다른 요청 번호로 같은 물건을 동시에 회수해도 한 건만 성공하고, 나눠서 동시에 도착 기록해도 전량 완료·미도착 해제·상태 이력 4건 유지.
- 초기화와 이전 버전 회수의 동시 실행을 10회 반복. 순서와 무관하게 초기화 이후 이전 회수 기록이 남지 않음.
- SQL 주입 문자열·다른 기계의 물건·중복 물건·다른 회수 물건·중복 JSON 키·깊은 JSON·과대 요청·외부 Origin/Host·정적 파일 경로 이탈 거절을 확인.
- 새 버전 검사 값은 공개 대시보드에서 얻는 **오래된 요청 방지 값**이다. 직원 인증 수단이 아니며 실제 API의 키 검증을 대신하지 않는다.

- 보완 전 Python 초기 공격 6개 메서드 중 5개에서 실패(하위 입력 사례 포함 8개 단언 실패), 1개 통과. 현재 모든 공격 회귀 통과.

- 신규 Python 공격 회귀 10개 포함 **전체 513개 실행, 실패 0개·환경 조건 14개 생략**.

## 남은 한계와 다음 단계

1. 실제 직원별 로그인·권한·감사자 식별이 없다. 기존 실제 API는 공유 직원 키 방식이고, 시연은 로컬 가상 저장소만 사용한다. 실서비스 배포 전 직원 인증·권한을 연결해야 한다.
2. 이번 실행은 실제 PostgreSQL 미연결이다. SQLite와 PostgreSQL은 별도 구현이므로 팀 DB 연결 후 경쟁 회수·부분 도착·롤백·권한을 같은 시나리오로 검증해야 한다.
3. 자동 지연 판정 시각·스케줄·실제 알림은 미연결이다. 기존 알림 전송은 전송 후 DB 커밋 직전 중단되면 중복 전송 가능성이 있으며 외부 수신 측 중복 억제·재전송 정책 검토가 필요하다.
4. 실물 수량·물건 대조는 사람이 수행한다. 이 시험으로 실제 회수 누락 0건을 입증하지 않는다. 현재 실행 도구의 127.0.0.1 바인딩을 유지해야 한다.
