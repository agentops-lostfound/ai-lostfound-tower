# LF-5·LF-9 sLLM 연동 오류 점검 및 보완

## 수정한 문제

1. 안내와 물건 검색을 함께 요청하면 `generation_used`만 남고 모델 이름·실행 결과가 사라졌다. 혼합 응답에 `generation_status`, 실제 사용 시 `model`, `guidance_status`, `search_status`를 보존한다. 기존 최상위 `status`와 후보 카드 형식은 유지한다.
2. 설명 입력 화면의 채팅 API는 RuntimeError 내용을 응답으로 내보냈다. 합성 비밀 문자열 노출을 재현한 뒤, 이 경로의 503 응답을 일반 안내로 바꿨다. 유효성 검사 422는 유지한다.
3. 모델의 `done=false` 응답에 유효한 JSON이 들어 있으면 성공으로 취급했다. 미완료 응답과 길이 제한 종료는 문서 원문 안내로 대체한다. 기존 테스트·주입 인터페이스와 호환하기 위해 `done` 필드가 생략된 응답은 종전대로 문단 검증을 수행한다.

## 연동 시험

- 모델·DB 오류 재현 시험은 수정 전 실패, 수정 후 통과했다. 모델 지연 중 다른 안내 질문은 문서 원문으로 돌아가며, 별도 물건 검색은 계속 동작한다.
- 실제 인증 연결이 없는 PostgreSQL 모드에서는 안내가 성공해도 DB 검색을 실행하지 않는다. 인증 토큰과 실제 접수 번호가 모델 입력에 들어가지 않는 것을 확인했다.
- `tests/test_sllm_collection_workflow.py`: 임시 SQLite 안에서 기존 설명 확인 API, 모델 안내·검색, 회수 API, 부분·전체 도착, 통계를 연결했다. 시험 전용 뷰가 두 시연 스키마를 연결하며, 실제 DemoItemDatabase 검색과 DemoCollections 회수 코드를 그대로 실행한다.
- 지갑 설명 확인 → 검색 1개 → 지갑·USB 회수 후 지갑 검색 0개 → USB만 도착 시 0개·누락 알림 1개 → 지갑 도착 시 검색 1개·알림 0개. 접수 통계는 모든 단계에서 지갑 1개로 유지됐다.
- 회수 중 모델 장애를 주어도 문서 안내·DB 조회가 유지되고 회수 중 물건이 후보로 돌아오지 않았다. 중복 회수·도착 후 회수 묶음 1개, 상태 기록 4개로 유지됐다. 예약은 생성하지 않았다.
- 이 뷰는 임시 시험에만 존재한다. 실행 중인 8110·8111·8112의 개별 시연 DB를 실제로 공유하도록 바꾼 것은 아니다.

## 검증 결과 및 로컬 적용

| 검증 | 결과 |
|---|---|
| LF-5 Python 전체 | 797건, 실패 0, 건너뜀 13 |
| 회수 관리 통합 Python 전체 | 802건, 실패 0, 건너뜀 14 |
| Node 화면 로직 | 38건 통과 |
| 실제 `qwen3-vl:2b-instruct` HTTP 질문 | 11/11 통과 |
| 실행 중 8111·8112 혼합 질문 | 두 서버 모두 `generation_status=generated`, `search_status=items_found`, 후보 1개·근거 1개·예약 없음 |

기존 실제 모델 검증 도구에 안내·검색 혼합 질문을 추가했다. 모델은 근거 문단을 선택하는 방식이며 자유로운 문장 생성·의미 검색 성능 검증은 아니다. 사진 분석·음성 인식의 실제 장치 정확도는 이번 작업에서 시험하지 않았다.

Docker 엔진이 실행되지 않아 실제 PostgreSQL 시험은 이번에 실행하지 못했다. 건너뛴 시험을 통과로 계산하지 않는다. 실 운영 인증·팀 DB·로봇 연동은 미완료이며 가상 시나리오 통과로 대신하지 않는다.

실행 중 설명 입력(8111)과 챗봇 미리보기(8112)를 재시작해 수정 코드를 반영했다. 기존 회수 시연 DB는 수정·초기화하지 않았다. 공유 계약·main·GitHub·Jira는 변경하지 않았다. 이번 변경은 사용자 요청에 따른 챗봇 지원·회수 관리 연동 검증이다.
