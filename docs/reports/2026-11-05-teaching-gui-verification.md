## raised 실패 분석

### 미세 스텝 판정 변경 (사용자 요청 후)

각 스텝의 runtime action ACK만 확인하면 pending을 해제한다. 매 스텝 실측 오차 0.15 도착을 기다리던 조건은 제거했다. 최종 도착 기준 0.15는 유지한다. 다음 목표가 현재 실측보다 0.45 normalized 이상 앞서면 전송하지 않고 기다리며, 1.5초 동안 이 조건이 지속되면 소프트웨어 정지를 요청한다. 서버의 기존 0.5 제한과 명령당 0.25 제한은 그대로다. 이는 충돌 감지나 물리 속도 제한이 아니다.

최종 목표에서도 도착하지 못하면 별도의 대기 후 정지한다. STOP/통신 노후/미승인 실행 차단은 유지한다. 실제 서버·실행 중 GUI에는 hot patch하지 않았다. GUI 재실행 후 적용된다. 속도3에서 실측이 전혀 변하지 않으면 두 번째 0.25 스텝은 0.45 제한에 걸려 여전히 멈출 수 있다. 이 경우 제한을 계속 키워서 돌파하지 않는다.

검증: runtime ACK 후 위치 미도착 상태에서 pending 해제, 0.1 단계 목표 누적 후 모의 추종 가능, 정체 시 무한 누적 방지 시험 추가. 전체 285개 중 284통과/DB1스킵. 실물 성공은 아직 미검증.

### 후속 실물 시도 로그 분석 (14:38 KST)

사용자 승인으로 실행한 첫 명령에서 중단됐다. ACK 최초 0.078초, 피드백 45개/1.515초 동안 실측 6관절 벡터는 전부 동일했다. wrist_flex 목표 84.686172, 실측 84.936172, 차이 0.25. 읽어온 등록 보정 범위 990..3340 기준 손목 목표 변화는 약 3 encoder ticks다. 단순 반올림만으로 목표가 같은 tick이 되는 경우는 아니다. 미세 동작 데드밴드/부하 정체 가능성은 있으나 확정하지 않았다.

설치된 코드 경로 확인: runtime → SharedRobot.send_action → owner worker → SO101.send_action → normalized를 정수 tick으로 변환 → sync write. SharedRobot.send_action은 fire-and-forget이며 action 텔레메트리가 실제 모터의 수신 확인은 아니다. 최근 컨테이너 로그에 follower 쓰기 실패 경고는 확인되지 않았으나 이것만으로 버스 수신/토크 상태를 증명하지는 못한다. leader 초기 관측 지연 경고는 있었지만 이번 follower 정체의 원인으로 단정하지 않았다.

이번 조사에서는 실물 추가 이동, 허용치 확대, 모터 PID/보정 수정, 프로세스 재시작을 하지 않았다. 완전한 원인 확인에는 모터 소유 프로세스를 통한 goal/present/torque 상태 진단이 필요하다. 동일 serial을 별도 프로그램에서 열지 않는다.

기존 failure는 acknowledged=true, position_confirmed=false. wrist_flex 오차 0.200, elbow_flex 0.1657로 0.15를 초과했다. 명령값이 runtime actions에 반영됐다는 뜻이지 실제 모터 도착 ACK는 아니다. 과거 단일 스냅샷으로 기계적 정체, 양자화/데드밴드, 피드백 지연 중 원인을 확정할 수 없다.

매 미소 스텝마다 도착을 기다리는 구조라 작은 목표 변화가 실제 구동기의 유효 분해능보다 작으면 정체할 가능성은 있다. 아직 가설이며, 이를 이유로 허용치를 확대하거나 실물 이동을 반복하지 않았다. 다음 승인된 시험에서 motion_trace.jsonl로 오차가 줄어드는지/동일 값에 고정되는지/ACK가 지연되는지 확인해야 한다.
