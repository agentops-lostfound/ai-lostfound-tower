# LF-3 Qwen 지연 검토 및 개선 제안

2026-11-03 · 검토자 pil2ya · 분석 문서이며 성능 개선 구현/실측 완료가 아니다.

## 확인 범위

팀원 인계와 LF-3-yolo-aruco 브랜치의 91c4a88을 대조했다. vision/sequence.py, qwen_worker.py, item_features.py, TOPVIEW.md, TOPVIEW_VALIDATION.md를 읽었다. 현재 작업 브랜치는 pil2ya로 유지하며 팀원 코드를 변경하거나 병합하지 않았다.

인계의 장비·환경은 RTX 3050 6GB, Windows, Qwen3-VL-2B-Instruct, NF4 4-bit, float16/SDPA다. 외부 qwen 프로젝트와 GPU 실행 환경은 여기서 확보·검증하지 않았다. 보고된 시간은 팀원 측정이며 이번 검토에서 재측정한 수치가 아니다.

## 코드로 확인한 병목 구조

- run_sequence는 요청마다 subprocess.Popen으로 Qwen 프로세스를 시작한다. Python/import·모델 로딩 비용이 새 요청마다 발생한다.
- worker는 crop을 순차 처리하며 extract_item_features를 호출한다. 추출 함수는 crop마다 load_model을 호출하지만 외부 로더의 캐시 구현은 제공되지 않았다. 한 실행 내 모델 재사용은 팀원 설명이며 캐시가 실제로 어떻게 보장되는지는 외부 소스 확인이 필요하다.
- max_edge=512, offline=True는 worker에서 명시한다. max_new_tokens와 retries는 외부 Settings 값이므로 실제 수치를 알 수 없다.
- 매 시도마다 processor.apply_chat_template로 이미지·긴 지시문·8키 템플릿을 처리한다. do_sample=False이며 이미 torch.inference_mode를 사용하므로 이를 새 개선으로 제안하지 않는다.
- 검증 실패 시 수정 지시를 붙여 이미지 입력부터 전체 생성까지 반복한다. 검증은 키·자료형·스티커 일관성을 확인하며 시각적 정확도는 보증하지 않는다.
- inference_seconds는 processor·generate·decode·검증·재시도와 실패 로그 저장을 합친 값이다. 순수 생성 시간이나 tokens/s로 해석할 수 없다.
- 전체 시퀀스의 보고된 51.3초 중 3.7초는 검출, 8.3초는 모델 로딩, 30.2초는 두 crop 생성·검증이다. 차액 약 9.1초는 미분리 비용이며 전부 import라고 단정하지 않는다. 이후 51.5초 사례 및 립밤 사례와 합산하지 않는다.

## 권장 첫 실험

1. 모델·양자화·의존성은 고정하고 baseline을 계측한다. 고정 crop의 파일 목록·해시, 프롬프트 버전, 출력 한도·retry 설정을 로컬에 기록한다.
2. 상주 worker 한 개와 제한된 FIFO 대기열을 둔다. ready 상태, 요청 ID·물품 ID 매핑, timeout·실패·재시작·취소 규칙을 명시한다. 한 실행 중 캐싱만으로는 요청 간 상주가 되지 않는다.
3. worker에 요청 A/B를 연속 전달해 B에서 모델 로딩이 재발하지 않는지 확인한다. 첫 실제 추론은 CUDA 초기화 등의 비용이 있으므로 warmup 전후를 분리한다.
4. 같은 8키 스키마로 짧은 프롬프트와 값/목록 길이 제한을 비교한다. 토큰 상한은 정상 결과의 실제 길이를 확인해 정한다. 필드 제거는 소비자 계약 협의 없이 하지 않는다.
5. 512와 작은 해상도를 비교하되 문자·스티커 실패가 늘면 텍스트가 필요한 crop은 고해상도를 유지한다. 별도 OCR은 정확도와 추가 지연을 함께 검증한 뒤 선택한다.

6GB를 로봇 정책·Ollama와 공유한다면 상주 worker에 unload/reload 기능과 GPU 소유권 전환이 필요하다. 모델을 계속 유지하라는 권고가 동시 모델 상주를 허용하는 것은 아니다. 현재 팀 main의 Ollama 4B 검토기와 이 비전 HF 2B 경로는 서로 다르며 22토큰·2.7초라는 검토기 측정값을 이미지 특징 추출 성능으로 비교하지 않는다.

변하지 않은 물품을 반복 관찰한다면 등록 특징 재사용과 대상 crop만 상세 분석하는 흐름도 후속 후보이나, 물체 이동·가림·오인식 시 캐시 무효화와 개체 연결이 필요하다. 이를 구현하기 전 기존 모든 crop 분석을 생략하지 않는다.

## 측정 설계

- 프로세스 시작부터 ready까지 import·모델·processor 로딩을 각각 측정. 부모에서 왕복 시간을 별도 측정한다.
- crop별 이미지 전처리, chat template/processor, CPU→GPU 전송, generate, decode, validation, retry별 시간, 저장 시간을 분리한다.
- GPU 구간은 CUDA 동기화 경계를 명확히 하거나 CUDA events로 측정한다. CPU 타이머만으로 비동기 커널 시간이 끝났다고 간주하지 않는다. 같은 동기화/계측 조건으로 전후 비교한다.
- prefill과 decode 분리는 generate 호출 전후 타이머만으로 되지 않는다. 모델 호환 profiler 또는 첫 forward/후속 decode 구분 계측이 필요하며, 지원 확인 전에는 generate 전체 시간으로 보고한다.
- 시도별 입력 토큰·출력 토큰·image_grid_thw, 시도 횟수, 실제 장치 배치와 CPU offload 여부, peak allocated/reserved VRAM 및 프로세스 GPU 사용량을 기록한다. 시각 토큰 수는 해당 processor/model의 merge 규칙을 확인해 계산한다.
- 권장 비교는 같은 고정 crop 세트, 별도 cold 시작 3회 이상, warm 20회 이상으로 시작한다. 표본 수·중앙값·범위를 보고하고 p95는 작은 표본에서 참고치로만 취급한다. 이 반복 횟수는 제안이지 팀 확정 사양이 아니다.
- 전후 지연과 JSON 성공률뿐 아니라 품목·색·문자·재질·스티커 오류, 근거 없는 특징, unknown 처리 비율을 사람이 만든 정답과 비교한다.
- Windows 전원 모드, GPU 사용 프로그램, 모델 동시 실행, 입력 순서와 warmup 조건을 고정한다. 캐시된 model_load_seconds를 crop별로 더하지 않는다.

## 구현 전 필요한 외부 자료

외부 qwen 프로젝트의 config/settings.py, src/model_loader.py, src/image_preprocess.py, src/benchmark.py를 비밀값 없이 확보해야 한다. 실제 max_new_tokens/retries, 캐시 키·수명, processor 픽셀 설정, device_map/offload·KV cache 설정을 확인한다. 원본 사진·실행 로그·결과 JSON·가중치는 커밋하지 않는다.

현재 코드의 재현 명령은 팀원 브랜치 vision/TOPVIEW.md에 있다. pil2ya에는 해당 비전 코드가 없으므로 실행 가능한 개선 명령·전후 속도 향상을 이번 분석의 성과로 주장하지 않는다. 다음 구현은 계측과 상주 worker부터 독립적으로 검토하고 공통 contracts·클래스 순서·기존 외부 환경을 보존한다.
