## 목적과 사용자의 결정

- AI 분실물 관제탑: 카메라 → YOLO bbox/크롭 → Qwen 특징 JSON → 사람의 한국어 설명과 매칭 → 선택 물품 좌표를 로봇에 전달.
- YOLO 클래스 정확도보다 개별 물품 검출·크롭이 중요하다. 같은 종류끼리 놓고 외형 차이가 명확한 물품으로 시연하는 방향. 립밤 미검출 튜닝·학습은 보류했다.
- 지금 우선순위는 풀 파이프라인 연결이다. 검출 실패 재시도·중복 검출 정책은 이후 보강한다. 실행 complete를 모든 물품 검출 또는 특징 정답으로 보고하면 안 된다.
- Qwen 스티커 오인식 하나 때문에 정답 후보 전체를 탈락시키는 것을 원하지 않는다. 모순된 스티커 정보만 제외하는 방향이다. 색 등 다른 정책을 무조건 완화하라는 뜻은 아니다.
- 별도 메인 언어 모델은 사용하지 않는다. 한국어 선추출 방식을 잠정 채택했다. STT는 독립 모듈이다.
- 사용자에게 긴 확인 질문을 반복하기보다 가능한 작업부터 진행하고 결과를 짧게 설명한다. 디스코드는 요청 시 복사할 문안 제공, 전송은 별도 지시가 필요하다.

## 현재 모델과 실행 환경

- YOLO 기본 `models/yolo26m.pt`, confidence 0.25, imgsz 640, crop padding 0, 보통 CPU. n/s/m/l/x 비교 후 m을 선택했다. 낮은 임계값은 오검출 증가로 채택하지 않았다.
- Qwen3-VL-2B-Instruct, RTX3050 6GB, NF4 4-bit, float16/SDPA. max edge 512. 외부 모델 캐시를 재사용한다.
- CPU 매칭: FastEmbed all-MiniLM-L6-v2, 영어 텍스트 임베딩 384차원. 점수는 확률이 아니다.
- STT: faster-whisper large-v3-turbo, 별도 .venv-speech, GPU lease 공유. 합성음성 smoke test와 실제 녹음 테스트는 구분한다.
- `.venv-vision`은 Python3.11.18, torch2.9.1 CPU, ultralytics8.4.199, OpenCV4.14. `.venv-query`는 한국어 파서/로컬 OPUS용이며 비전 패키지를 참조한다.
- 외부 Qwen의 낡은 .venv 실행기는 사용하지 않는다. 아래 실제 Python과 site-packages를 사용한다.

```powershell
cd C:\Users\user\AI-LostFound\team-repo
$env:PYTHONIOENCODING='utf-8'
& ..\.venv-vision\Scripts\python.exe -m unittest discover -s tests

# YOLO + ArUco만
& ..\.venv-vision\Scripts\python.exe -m vision.scripts.test_vision --image 'C:\Users\user\Pictures\Camera Roll\WIN_20261105_09_33_00_Pro.jpg' --device cpu

# YOLO → 크롭 → Qwen
$env:QWEN_MAX_EDGE='512'
& ..\.venv-vision\Scripts\python.exe -m vision.scripts.run_sequence `
  --image 'C:\Users\user\Pictures\Camera Roll\WIN_20261105_09_33_00_Pro.jpg' `
  --qwen-root '..\qwen' `
  --qwen-python '..\qwen\.python\cpython-3.11.18-windows-x86_64-none\python.exe' `
  --qwen-site-packages '..\qwen\.venv\Lib\site-packages'
```

Qwen/STT/VLA는 agents/gpu_lease.py의 GPU 사용권을 공유한다. 다른 GPU 작업을 무시하거나 임의로 상주 실행하지 않는다.

## 구현 진입점

- `vision/vision_pipeline.py`: YOLO/ArUco, crop, debug.jpg, result.json.
- `vision/sequence.py`: 외부 Qwen subprocess, 진행률·취소·부분 결과, 촬영 시각과 GPU lease.
- `vision/item_features.py`: 일반 물품 8필드 스키마. category/colors/shape/materials/logos_or_text/sticker_status/stickers/distinctive_features。
- `agents/vision_adapter.py`: 현재 canonical adapter. 분석 complete·Qwen 정상·알려진 category·유효 보정 등을 충족하면 center_mm를 제공한다. other/unknown은 mm를 허용하지 않지만 매칭에서 즉시 품목 불일치로 전부 제외한다는 뜻은 아니다.
- `matching/`: KoreanFirstParser → 속성 비교 + MiniLM 자유문장 비교. 한국어 추출 후 자유구절만 로컬 OPUS로 번역한다. 색·품목은 정규화한다. 미지원 단어·부정·모호성 처리 한계가 남아 있다.
- `run_pipeline.py`: 이미지 또는 기존 vision report와 text/query-file/audio로 검사 보고서를 만든다. CLI는  `--help`와 `docs/design/pipeline-runner.md`. 후보의 동일 object_id에 coordinate_chain을 연결한다. 직원 확인 필요, robot_authorized=false.
- `vision/installation_coordinates.py`: 이번에 추가한 좌표 연결. bbox 중심 px 재계산 → 원본 H → 작업대 XY → 설치 XY + 고정 Z. CLI도 제공한다.

## 좌표와 실물 설치 — 가장 중요한 최신 기준

사진 전용 400mm 입방 박스는 구매했지만 당시 배송 전이었다. 현재 카메라는 모니터에 달린 약400mm 높이의 대각뷰다. 카메라 높이400과 로봇 고정 Z280은 다른 값이다. 사용자에게 재확인 없이 혼동하지 않는다.

- 로봇은 보관함 밖 입구 중앙에 설치. 바닥 회전축 중심 → 입구 **106mm** (100/104는 과거값).
- 입구 → 마커 공유 꼭짓점 직사각형의 아래 긴 변 **37mm**. 직사각형 가로324 × 세로150mm, 좌우 중앙 정렬. 보관함 내부 바닥은 설치면보다7mm 높다.
- ArUco `DICT_4X4_50`, 검정 사각형 변14mm. work 좌표:
  - ID0: [[0,14],[0,0],[14,0],[14,14]]
  - ID1: [[338,178],[338,164],[352,164],[352,178]]
- 오늘 카메라에서는 ID0이 화면 오른쪽 아래, ID1 왼쪽 위다. 화면 방향이 바뀌었다고 물리 마커를 옮기지 않는다. 사용자 지시: 현재 배치 고정.
- 잠정 installation 원점: shoulder_pan 축을 설치면에 수직 투영한 점. 로봇 뒤에서 보관함을 볼 때 +X 오른쪽, +Y 보관함 안쪽, +Z 위.
- 변환: `X_install=176-x_work`, `Y_install=129+y_work`. ID0 공유점 work(14,14) → (162,143), ID1 공유점(338,164) → (-162,293).
- 고정 접근 Z=280mm는 잠정 installation 좌표의 절대값. 바닥7mm를 더하지 않는다. 집기 높이나 물체 표면 높이로 측정된 값이 아니다.
- `vision/configs/installation.yaml`에서 matrix/offset_mm/approach_z_mm와config_version 조정. measurements_mm는 기록만 하므로 이것만 변경하면 변환식이 자동 계산되지 않는다.
- 결과에 설정 스냅샷/SHA256, 원본 마커 배치 스냅샷을 저장. 배치 기록이 없는 옛 결과는 work_frame_unverified로 설치좌표를 보류한다. 실패 보정·잘못된 bbox에서도 좌표를 보류한다.
- **수정 가능성이 높은 잠정 구현**이다. controller_frame_verified=false, robot_authorized=false. 실물 제어기의 원점/축/단위/TCP는 아직 확인하지 못했다. 현 브랜치 robot/에는 README만 있고 agents의로봇동작은 MockBackend다. 실제 연결·모터 이동은 하지 않았다.
- main에는 이 브랜치와 다른robot_approach(center_mm,center_px)/robot_home 약속이 확인됐으나 가져오거나 병합하지 않았다. 현 브랜치는 robot_approach(center) 픽셀 약속이 남아 있다. 이 차이를 확인한 뒤 연결해야 한다.

마지막 run은 대응점8개, 최대 재투영 잔차0.339mm다. 이것은 로봇 실제 오차가 아니다. 마지막 전체 테스트248개,247통과·DB1스킵.

매칭은 색/품목의 코드 비교와 자유문장 임베딩을 함께 쓴다. 임베딩만으로 색 반대 문장도 높은 점수를 받는 문제 때문에 보강했다. 보류/1·2위 차이/coverage/속성 기준은 matching/configs/matching.yaml. 수치는 실험용이며 확률이나 실전 정확도 보장이 아니다. 한국어 원문 처리와 사진 정답 검증이 별개임을 유지한다.

로봇 도달 시뮬레이션은 `outputs/box_reach_review/full_floor_results.json`, `reach_check.py`. main의 축척1.6 시각화를 그대로 실제도달로 해석하지 않았고 축척1 기준을 별도로 계산했다. 사용자는 안 닿는 영역에 물건을 두지 않는 방식을 수용했다. 벽 충돌·실제TCP·수직그리퍼 검증은 없다.

## 다음 작업

1. 로봇 담당자의 실제 제어 코드 위치/브랜치를 확인한다. 실제 base 원점, XYZ 방향, mm/m, TCP와요구입력을 확인한다. 현 repo만으로 확인됐다고 보고하지 않는다.
2. 확인된 제어기 좌표에 잠정 installation 프레임을 연결한다. 필요 시 독립 실측 대응점으로 보정하고설정 버전을 올린다. 고정 Z도 실제 의미를 확인한다.

4. 이후 검출 누락/중복/장면 노후화 정책, 물체 높이 시차와bbox 중심≠파지점 문제를 보강한다. 지금전부 튜닝하는 쪽으로 범위를 넓히지 않는다.
