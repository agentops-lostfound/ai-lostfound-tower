## 1. 프로젝트·사용자 의도

- 고정 탑뷰 카메라로 물품 검출 → 크롭 → Qwen 특징 JSON → 사용자 설명과 비교 → SO-101/SmolVLA 반환 연동 프로젝트.
- YOLO는 정확한 의미 분류보다 bbox·중심·크롭 확보가 중요하다. 물품 종류·색·세부 특징은 Qwen 담당.
- MVP는 같은 종류 물품끼리 배치하고 외형 차이가 명확한 물품을 선정하는 방향. 립밤은 시연 대상에서 제외하는 쪽으로 논의했으며 실제 일관된 검출은 아직 부족하다.
- 한국어 자연어 입력을 CPU 전처리·MiniLM으로 매칭한다. 메인에서 별도 언어 모델을 사용하지 않는다고 사용자 확인.
- 한국어 선추출 방식을 잠정 채택했고 독립 STT를 추가했다. 실물 로봇·메인 연결은 아직 준비 단계.
- 한국어로 간결하게 설명. 사용자는 직접 CLI 실행·결과 관찰·팀 공유 보고서와 디스코드 문안을 선호한다. 디스코드는 문안만 제공했고 전송하지 않았다.

## 4. 비전 구현·설정·실패

- vision/configs/vision.yaml: yolo26n.pt, confidence=0.25, imgsz=640, padding=0. 보통 CLI --device cpu.
- 낮은 confidence 0.15/0.12/0.10 시험은 오검출과 잘못된 클래스가 늘어 원상복구했다. threshold를 계속 낮추는 것을 해결책으로 합의하지 않았다.
- 기본 COCO에서 지갑·립밤·USB·보조배터리는 안정적으로 잡히지 않는다. USB 등이 cell phone으로 검출돼도 품목 학습 성공이 아니다.
- item 단일 클래스 학습용 별도 설정·스크립트는 준비했으나 실제 데이터 수집/라벨링/학습은 하지 않았다. Roboflow 후보 논의만 있었고 확정·다운로드·학습 완료가 아니다.
- bbox 원래 중심을 center_px로 기록. ArUco 유효 때만 center_world_mm; 현재 markers_mm={}라 null. Dictionary=DICT_4X4_50, 재투영 오차 기준 3mm, inlier ratio 0.75.
- 한 마커의 모서리 4점만으로 계산 가능. 마커 4개 강제 조건은 현재 없음. 재투영 오차와 작업대 전체의 독립 실측 오차는 다르다.
- 렌즈 왜곡·물체 높이 시차·bbox 중심과 파지점·작업대→로봇 좌표 변환은 별도 검증 전.
- run_sequence: 검출 → 크롭 → 격리 Qwen subprocess → result_with_qwen.json. 하트비트, 부분 실패/취소 보존. complete는 실행·스키마 성공이지 시각 정답 아님.
- Qwen 필드: category, colors, shape, materials, logos_or_text, sticker_status, stickers[{shape,position}], distinctive_features. 스티커 상태/목록 모순은 재시도 후 실패 기록하며 임의 보정하지 않는다.
- 현재 사진군에서 Qwen 재시도 없는 추론은 물건당 약 7~15초. 순차 처리하므로 대략 N×7~15초 + 최초 로딩·검출·프로세스·저장 오버헤드. 재시도하면 더 길다. 로딩을 물건 수만큼 곱하지 않는다.

## 5. 매칭 구현과 실험

- matching/embedding.py: sentence-transformers/all-MiniLM-L6-v2, FastEmbed ONNX, CPUExecutionProvider, 384차원, 벡터 캐시 .cache/matching.
- 영어용 모델. 한국어를 MiniLM에 직접 넣지 않는다. 코사인은 정답 확률이 아니며 후보 점수 합이 1일 필요 없음. 벡터 DB·pgvector는 이 모듈에서 사용하지 않는다.
- matching/hybrid.py: 품목·색 먼저 필터 → 남은 후보 자유 특징 임베딩 → policy.py가 결합/판정. 미언급과 absent 구분. 불확실 Qwen 정보는 보류 가능.
- 상태 matched/needs_confirmation/no_match. matched일 때 selected_id. 공통 계약의 index·uncertain/none과는 어댑터가 필요하다.
- 설정 matching/configs/matching.yaml: weights category .2 / color .5 / sticker .1 / semantic .2; min_score .65, min_margin .10, coverage 1.0, min_attribute_score .8. 실험값이지 검증된 확률 기준이 아님.
- 관계 wallet↔card_wallet=.8; blue↔navy=.6, blue↔dark blue=.8, navy↔dark blue=.9. 알려진 품목/명확한 색 불일치 제외 기본 켬.
- 기존 10그룹·17특징·34질문(긍정17/모순17): 초기 정책 목표 확정10·보류7 → 개선 정책16·보류1, 모순17개 no_match 유지. Qwen 값을 보고 만든 약한 정답·중복·단일 후보 포함. 일반 정확도로 보지 않는다.
- 남은 보류는 실제 검은 폰인데 Qwen category=other. 사용자 확인만으로 raw Qwen을 덮어쓰거나 기준을 낮추지 않았다.
- 실제 vpu의 7질문: 폰/배터리 선택, USB는 Qwen 색 오류로 오제외, 배터리 스티커 충돌 보류, 노란 지갑 no_match, 정보 부족/케이스 보류.
- 일반 자유 특징 부정(예: 파손 없음)은 임베딩에서 반대 후보를 선택하는 문제가 남아 있다.

## 6. 한국어 전처리 — 현재 잠정 결정

```text
한국어 원문 → 한국어 규칙·사전 추출+원문 span
 → 품목·색·스티커 유무 표준값 변환
 → 손상·위치·정도를 유지한 원문 구절만 OPUS-MT 번역
 → 기존 매칭
```

- matching/korean_query.py의 KoreanFirstParser. 한국어 추출은 추가 LLM이 아니라 코드 규칙이다. source start/end와 근거 구절, 부정색·부품색·라틴 글자를 보존한다. 특징을 후보 정보에 맞춰 생성하지 않는다.
- 고유 라틴 글자와 iPhone 브랜드는 사전 보존. 자유 구절의 손상 누락·금→gold 혼동 일부를 경고하나 완전한 의미 검증은 아니다.
- requires_review=true라 한국어 전처리 경로의 최종 판정은 보류. 정책 자체의 선택 결과와 실제 최종 결과를 구분한다. 이 제한을 임의 제거하지 않는다.
- 기본값: demo_query_parser mode=korean-first, rank_items --parse-korean backend=korean-first, evaluate_translation translator=korean-first.
- 기존 직접 Qwen, Qwen 통번역, OPUS 통번역, DeepL 옵션은 비교용 유지.

| 방식 | 자료·결과 | 변환 중앙값 |
|---|---|---:|
| Qwen3-0.6B 직접 영어 JSON | 8문장 검사 필드 일치2/8, 환각·부정 오류 | 12.12초 |
| Qwen3-0.6B 전체 번역→영어 규칙 | 동일20문장 세 속성 일치10/20 | 2.52초 |
| OPUS-MT ko-en 전체 번역→영어 규칙 | 동일20문장14/20 | .51초 |
| 한국어 선추출→자유 구절 OPUS | 동일20문장20/20, 번역16회 | .26초 |

마지막 수치는 이미 본 문장으로 규칙을 만든 개발 세트의 category/colors/sticker_status 일치다. 번역 정확도·검색 정확도100%가 아니다. 호출 생략4문장이 중앙값에 포함된다. 포켓몬·파손 위치·구어체 누락·금→gold는 남는다.

20문장×기존11그룹(22특징)=방식별220비교. 최신 주 그룹 정책은 목표 있음14개 중 목표선택11·보류3, 없음4개 중 거절2·보류1·오선택1, 모호2개 보류. 실제 최종 선택은 검토 제한 때문에 하지 않았다.

팀원 재현 자료: matching/configs/evaluation_candidates.json(11그룹), vpu_candidates.example.json(5개), translation_20_cases.json. 세 방식 실제 결과 요약은 matching/reports/translation_comparison_results.json. 원본 전체는 outputs/matching/translation_20*, 공개 스냅샷에는 사진·좌표·절대 로컬 경로 없음.

## 8. 로봇 연결 논의 — 문서 계획이며 미구현

사용자 요청으로 원래 6항목 표를 우리 구현에 맞춰 검토했다. 현재 합의한 방향과 미확정 조건은 다음과 같다.

1. **마커1개로 시작**: 팀원 의견을 수용, 작업대 좌측 상단 마커1개로 원점/축 설정 후 여러 지점 실측. 정확도·가림 대응이 부족하면 추가. 원점=마커 중심/어느모서리인지, 크기·방향·베이스 변환은 현장 합의 전. 마커 원점과 Arm 베이스 원점은 자동으로 같지 않음.
2. **실측 검증**: 한 마커의 모서리4점으로 계산은 가능하지만 독립 측정점으로 근처·중앙·먼 쪽 오차 검증 필요. 기존4마커 필수·5mm 제안은 확정값 아님. 현재 코드3mm는 재투영 오차 기준뿐.
3. **정지/Home 분리**: 현재 tools.py/mcp_tools.md는 정지+Home 혼재, supervisor는 실패 때 robot_stop 호출. 정지만 수행하고 Home은 직원 확인 후 별도 버튼/명령, 정상 전달 후 대기 자세는 별도 결정하는 방향 수용. 계약·로봇 실행 코드는 아직 변경 안 함. Home자세·좌표원점·관절호밍을 혼동하지 않음.
4. **촬영 유효성**: 원래표600초는 해당 로컬 코드에서 확인 안 됨. 반환 시작 때 새 촬영, 촬영 시점 기준 유효시간, 이동 시 무효화·집기 직전 위치 재확인 계획. 120초는 제안값뿐이며 Qwen N×7~15초와 재시도 고려 후 결정.
5. **GPU 순서 제안**: STT 입력확정→STT 해제→촬영/Qwen→Qwen 해제→CPU 전처리·매칭→접근/VLA. 메인에서 사용권·실제 메모리 해제·취소·최대대기시간·직원확인 제어 필요. 아직 통합 제어 없음. 팀의 기존 Ollama4B 계획과 우리 Transformers2B 경로 확인 필요; Ollama keep_alive를 우리 프로세스에 그대로 적용하지 않음.
6. **재시도**: supervisor MAX_GRASP_ATTEMPTS=2(첫+1재시도). 실제VLA/위치재확인/집기검증 시험 후 조건 확정.

공통 계약 어댑터 미완성: vision_topview의 box/center/features(픽셀) 및 단수 color/mark/visible_text/material/confidence와 우리 raw 스키마가 다름. center_world_mm을 공통 center에 단위 확인 없이 넣지 않는다. 매칭 id/selected_id와 배열index·status 변환도 명시적으로 필요. 실제 CompositeBackend 연결·실물 로봇·DB·메인 UI 완료로 말하지 않는다.
